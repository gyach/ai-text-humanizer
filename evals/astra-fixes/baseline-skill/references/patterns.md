# Каталог редакторских решений

Оценивай дефект по последствиям для адресата. Сначала устраняй риск неверного понимания, затем тяжеловесность. Список помогает найти проблему; наличие слова само по себе её не доказывает.

| Признак | Решение | Граница |
|---|---|---|
| «Соответствующий», «данные», «при этом» с двумя возможными отсылками | Назови подтверждённый объект или покажи неоднозначность отдельно. | Не подставляй объект по догадке. |
| Пассив скрывает ответственность | Назови исполнителя, если он задан источником. | «Значение сохранено» может быть ясным описанием состояния. |
| Одна сущность названа разными словами | Используй термин задания/глоссария. | Не объединяй работника, пользователя и администратора без подтверждения их тождества. |
| «Быстро», «надёжно», «высокая производительность» без основания | Убери пустую оценку или сохрани проверяемую характеристику из источника. | Не заменяй эпитет выдуманными 200 мс или 99,9%. В рекламе допустима подтверждённая оценка. |
| «В рамках осуществления», «с целью обеспечения», цепочки отглагольных существительных | Найди действие: «Чтобы подготовить встречу, пришли таблицу». | Определённый юридический термин не заменяется бытовым синонимом. |
| «Является важнейшим шагом», «играет ключевую роль» | Скажи, что меняется и почему это важно, если это известно. | «Является» допустимо в точном определении. |
| «Обеспечивая», «способствуя», «тем самым» повторяют предыдущее | Удали пустой хвост, оставь уникальное последствие. | Причинная связь и наблюдаемое следствие сохраняются. |
| «Не просто X, а целая Y», механические тройки, натянутые противопоставления | Сформулируй конкретную мысль в нужном жанре. | Содержательное сравнение, риторика автора и перечень из трёх реальных пунктов допустимы. |
| «Возможно, стоит рассмотреть возможность» | Сократи до исходной степени уверенности или рекомендации. | Гипотезу не превращай в факт, рекомендацию — в обязанность. |
| «Вот текст», «Надеюсь, это поможет», предложение дополнительных услуг внутри документа | Удали служебную рамку ассистента. | Приветствие, благодарность и предложение помощи в настоящем письме могут быть его содержанием. |
| Рваные абзацы, одинаковые начала, тяжёлые предложения | Объединяй или разделяй по ходу мысли; меняй порядок слов для ясных связей. | Ни длинное предложение, ни повтор роли не требуют автоматической правки. |
| Жирное выделение каждой строки, декоративные заголовки и эмодзи | Оставь оформление, которое помогает пользоваться документом. | Соблюдай бренд, жанр и формат пользователя. Не исправляй разметку кода и служебные компоненты. |

## Смысловые повторы

Проверь соседние и удалённые фрагменты. Удали повторный пересказ одной мысли только после выделения уникальной информации каждого фрагмента. При частичном совпадении сохрани конкретное раскрытие, а сократи общую рамку. Причина, пример и последствие могут касаться одного правила и при этом сообщать разные сведения.

Самостоятельные REQ, пункты договора, критерии и шаги не склеивай ради краткости: отдельно читаемому пункту нужен свой контекст. Если объединение улучшит структуру, предложи его отдельно, когда такая перестройка не поручена.

## Русский синтаксис

Проверь согласование, управление, падежи после однородных членов, местоименные отсылки, пунктуацию и естественный порядок слов. Положение «только» проверяй по области действия. «Только администратор может отменить заявку» ограничивает роль; «Администратор может только отменить заявку» ограничивает действия.

Разбивая фразу, не теряй условие для второй её части. «При сбое сервис сохраняет черновик и уведомляет оператора» нельзя превратить в безусловное «Сервис уведомляет оператора».

В русской прозе используй «ёлочки», если это соответствует оформлению документа. Прямые кавычки в коде, цитатах и UI-литералах остаются дословными. Нормализовать оформление всего документа без запроса не требуется.

## Проверка сокращения: пример

Исходник: «Если проверка прав не пройдена, сервис не сохраняет запись. В этом случае запись не создаётся, а пользователь получает отказ и может запросить доступ у владельца».

Допустимо: «Если проверка прав не пройдена, сервис не сохраняет запись. Пользователь получает отказ и может запросить доступ у владельца».

Удалён только повтор о несозданной записи. Условие, отказ и возможность запросить доступ сохранены. Нельзя сократить до «Без прав операция недоступна»: исчезают конкретный результат и следующее действие пользователя.

## Недостающие факты: пример

Исходник: «При ошибке API возвращает соответствующий код».

Если коды не предоставлены, допустимо оставить предложение и вынести вопрос «Какие коды и тела ошибок возвращает API?». Нельзя добавить `400`, `401`, `422` как будто они подтверждены. Не вставляй «типичные» параметры и лимиты даже в пример конкретного продукта без явной маркировки вымысла и запроса на такой пример.
